What to build, in what order, and how to test each stage

Start: Wednesday, September 30, 2026

How to use this guide

The project is a pipeline. Each stage below has three parts: what to build, how to test it, and a Go/No-Go gate. Do not start a stage until the previous stage's gate has passed. If a gate fails, check the "If it fails" box and the Debugging Map (last page) before moving on.

DATASET ↓ TRAIN (FP32) ↓ QUANTIZE (INT8 + bit-exact simulator) ↓ EXPORT (model.json + model_data.c/.h + golden vectors) ↓ BUILD C RUNTIME (static buffers + dispatcher + kernels) ↓ RUN ON ESP32 ↓ VERIFY BIT-EXACT vs golden vectors ↓ BENCHMARK ↓ RESULTS TABLE + DEMO

The one rule above all: verify bit-exactness at every layer. Every stage's output must match a trusted reference before it feeds the next stage. This is what makes a 4-day build possible — you never debug two unknowns at once.

0.3 — Freeze the three contracts (write them in docs/, commit them)

ContractMust define
1. Requantize specINT8 weights + activations, int32 accumulators; requantize by fixed-point multiplier + shift; round-half-to-even; saturate to [−128, +127]; per-tensor scales; symmetric weights (zp = 0), asymmetric activations; the exact softmax algorithm (exp LUT or shift-based) — decide now, C will copy it exactly.
2. model.json schemaOrdered layer list: type (fc / conv1d / relu / softmax / flatten), input + output shapes, weight/bias tensor IDs into model_data.c, quant scales and zero-points per tensor, pad/stride/kernel-size for conv1d, total arena size.
3. Golden-vector formatJSON: one file per layer + one per full model. Fields: input (int8 array), expected output (int8 array), scales, zero-points, tolerance (0 = bit-exact). Generated by the Python simulator, consumed by C tests on host and ESP32.
GATE 0 — end of Day 1 morning: hello_world builds and flashes on the ESP32 · host CMake builds a hello test · the three contract docs are committed · repo pushed. Only now start Stage 1.
STAGE 1Day 1 — Train the Models (FP32)

Two small models. Do not chase high accuracy — the sprint proves the framework, not the model. Keep training under ~30 min per model.

1.1 — Pick the dataset (decide today)

OptionFeedsNotes
A. Synthetic sensor/gesture data (recommended)MLP + 1D-CNNNumPy-generated signals (e.g. sine / square / noise classes, or 3-axis synthetic gestures). Zero download time, fully controlled, easy class separation → accuracy ~99%.
B. Google Speech Commands subset (yes/no/up/down)1D-CNNReal keyword-spotting case study; download + preprocessing costs time. Use only if you already have it locally.
C. UCI HAR smartphone dataset1D-CNNReal sensor data, small download, moderate difficulty.

1.2 — Train (small on purpose)

ModelArchitectureINT8 size (approx)
MLPFlatten → FC 128 → ReLU → FC 64 → ReLU → FC n_classes~15 KB
1D-CNNConv1D(16, k=5) → ReLU → MaxPool → Conv1D(32, k=3) → ReLU → MaxPool → Flatten → FC n_classes~25 KB

Adam, cross-entropy, 10–20 epochs. Save the train/val/test split to disk — the same split must be reused later for the quantized-accuracy test (never re-split). Also save normalization constants (mean/std per feature): the C side must apply the same normalization as training.

GATE 1 — end of Day 1: both models trained · test accuracy printed (expect ≥ 95% synthetic, ≥ 85% real data) ⃛ FP32 weights + normalization constants saved · one command retrains both from scratch.
If it fails: low accuracy → check normalization and class balance; still low → make the dataset easier. Sprint scope beats model quality.
STAGE 2Day 2 Morning — Quantize (INT8) + Bit-Exact Simulator

This is the heart of the project. The NumPy simulator you build here becomes the golden reference that every C kernel is tested against.

2.1 — Post-training quantization (PTQ)

StepWhat to do
1. Collect activation rangesRun ~200 calibration samples through the FP32 model; record per-tensor min/max of every layer output (or use fixed ranges for ReLU nets).
2. Compute quant parametersscale = (max - min) / 255; zero_point = round(-min / scale) - 128 (int8). Weights: symmetric, zp = 0.
3. Quantize weightsq = clip(round(w / scale_w) + zp_w, -128, 127). Store biases as int32: b_q = round(b / (scale_in * scale_w)).

2.2 — Build the NumPy bit-exact simulator

It must replicate exactly what C will do — same operation order, same rounding:

  • int8 weights (symmetric), int8 activations; MACs in int64, accumulator kept as int32
  • requantize: fixed-point multiplier + shift, round-half-to-even, saturate [−128, +127]
  • ReLU in the int8 domain (clip 0..127 after requantize)
  • softmax: fixed-point exp per the spec (LUT or shift-based), int8 in → int8 out — write the exact algorithm in the spec doc now

2.3 — Quantized-accuracy check

Run the full test set through the simulator → quantized accuracy. Expect at most a 1–2% drop from FP32.

GATE 2 — end of Day 2 morning: simulator is deterministic (same inputs → identical outputs on re-run) · quantized accuracy within ~2% of FP32 · requantize spec updated with final multiplier/shift/rounding. Everything from here on is tested against THIS simulator.
If it fails: accuracy drop > 2% → widen the calibration set, use 99.9th-percentile clipping, and re-check zero-point arithmetic (off-by-one zero-point is the #1 PTQ bug).
STAGE 3Day 2 — Export Model + Golden Vectors

Generate everything the C side consumes. No C code may hardcode a shape or a scale — everything comes from these artifacts.

3.1 — Export artifacts

ArtifactContainsConsumed by
models/<model>/model.jsonLayer graph, shapes, kernel sizes, quant scales/zps, per-layer buffer sizes, total arena sizeC dispatcher (compiled in via a generated header)
models/<model>/model_data.c/.hINT8 weights, int32 biases, all scales/zps as C arrays — const, flash-residentlinked into firmware
tests/golden/<model>/Per-layer + full-model vectors (int8 arrays + scales + expected int8 outputs, tolerance 0)host tests + ESP32 tests

Tip: store weights row-major (C order) and state it in a header comment — C and NumPy must read the same memory layout. Generate a model_config.h with the arena size as a #define.

3.2 — How to test the exporter (round-trip test)

Parse the generated model_data.c back in Python, run the simulator on the re-imported weights, and confirm outputs are identical to the original run. This catches layout/precision errors before any C runs.

GATE 3 — end of Day 2 afternoon: round-trip test passes · model_data.c compiles standalone on the host · golden vectors exist for every layer of both models.
STAGE 4Day 2–3 — Build the C Runtime + Kernels

Order matters: host first, ESP32 second — the same kernel code is tested on host (fast, easy debugging), then run on target. Test each kernel in isolation against golden vectors before wiring the dispatcher.

4.1 — Build order (each row = one commit + one test)

#ComponentHow to test it
1Static arena + buffer manager (fixed regions, no malloc)Unit test: allocate/free patterns; assert no overlap; assert total size matches arena size from model.json
2Platform HAL (cycle counter, timer, print)Host: prints fake cycles. ESP32: esp_cpu_get_cycle_count() delta around a busy loop; cycles ≈ 240 MHz × measured wall time
3requantize_int32_to_int8 helperGolden vectors from the simulator: exact bit-match on ~1000 random int32 values across the scale range
4fc_int8 (fully-connected / GEMM)Per-layer golden vectors: bit-exact. Test both single-sample (N=1) and batched input
5ReLU + fixed-point softmax (exact spec algorithm)Golden vectors bit-exact; softmax outputs sum to ~255 within quantization resolution
6conv1d_int8 (with padding option)Golden vectors bit-exact for stride 1; test pad=valid and pad=same; test k=3 and k=5; cross-check 5 random shapes against the simulator
7Dispatcher: walks model.json, allocates buffers, calls kernels in orderFull-model golden vector: bit-exact end-to-end on host
8Benchmark harness (N inferences, cycles, ms, RAM, flash)Run naive vs optimized on host first (both must be bit-exact), then on ESP32

4.2 — Optimized kernels (same interface, same bit-exact rule)

After the naive versions pass, add optimized variants selected by a build flag or dispatcher config: packed weights + 4×-unrolled GEMM; im2col-free conv1d with sliding-window accumulation. Every optimized kernel must pass the exact same golden-vector test — optimized but wrong is worth nothing.

GATE 4 — end of Day 3: all kernels bit-exact on host · full-model inference bit-exact on host for both models · firmware compiles for ESP32 · full-model inference bit-exact on ESP32 · naive vs optimized cycle counts exist for at least the MLP.
If it fails: use the per-layer vectors to find the first layer where C diverges from the simulator, and debug only that layer (print the int32 accumulator for one output element in both). Nine times out of ten it is rounding or memory layout — not the math.

5.1 — Benchmark protocol (how to measure correctly)

MetricMethodValidity check

Peak RAMArena size (from model.json) + stack high-water mark; .bss/.data sizes from the .map file0xAA guard band after the arena, verified intact after a run — proves no overflow

Accuracy on targetPush test vectors over UART, run inference on ESP32, compare with simulator outputsBit-exact match → on-target accuracy = simulator accuracy automatically
Fairness rule: naive and optimized must be built with identical compiler flags (-O3, set globally in the build config, not per file) and run on identical inputs. Report the environment: ESP32 @ 240 MHz, ESP-IDF version, flags.

Debugging map — where to look when a test fails

SymptomCheck firstThen
C output ≠ golden vector (one layer)Rounding mode (half-to-even vs half-away), layout (row-major vs column-major), zero-point handlingPrint the int32 accumulator for one output element in simulator and C; diff at the first differing index
End-to-end mismatch but all layers pass aloneDispatcher buffer aliasing (a kernel overwriting its own input), wrong buffer indexRun the dispatcher with each layer writing to distinct buffers; re-enable overlap only after it passes
ESP32 result ≠ host C resultPlain char signedness (use int8_t/explicit types everywhere), alignment, optimization-dependent undefined behaviorBuild ESP32 at -O0 vs -O2; if results change, there is UB — run host build with sanitizers (-fsanitize=address,undefined)
Cycle counts unstableWiFi/BT active, other FreeRTOS tasks, cache effectsDisable radio, pin task to one core, warm-up runs, report the median
Quantized accuracy drop > 2%Zero-point arithmetic, calibration set too small or unrepresentativePercentile clipping; plot per-layer output distributions FP32 vs INT8 side by side
ESP32 hard fault during inferenceArena overflow (a buffer larger than declared), main-task stack too small0xAA guard band after the arena; increase main task stack in idf.py menuconfig

Golden rule: never debug two unknowns at once. Every stage has a reference (what correctness looks like) and a gate (when you may move on). The reference proves the stage is correct; the gate proves the pipeline is ready for the next stage.
